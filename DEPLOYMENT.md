# CRDPH — Computational Research and Data Processing Hub: Deployment Blueprint

This is the step-by-step plan for deploying `crdph.org` Next.js app on Vercel, with zero downtime and no lost search rankings.

---

## 1. Hosting choice: Vercel

For a marketing site plus lightweight CMS of this size, **Vercel** is the right default (Netlify works too — this project has been deployed there):

|                              | Vercel                            | Netlify                                | AWS Amplify                  |
| ---------------------------- | --------------------------------- | -------------------------------------- | ---------------------------- |
| Next.js App Router support   | Native (same company)             | Good, some feature lag                 | Good, more config            |
| Free tier                    | Generous (Hobby)                  | Generous                               | Pay-as-you-go, less generous |
| Startup / credits programs   | Vercel startup credits on request | Netlify startup & open-source programs | AWS Activate credits         |
| ISR / on-demand revalidation | First-class                       | Supported, different model             | Supported via SSR            |
| Ops overhead                 | Near zero                         | Near zero                              | Higher (more AWS knobs)      |

Recommendation: **Vercel Hobby to start**, upgrade to **Pro** (~$20/mo) only if
traffic or team-seat needs grow.

## 2. Pre-cutover checklist (do this first)

1. Create a **Supabase** project for production. From Project Settings →
   Database → Connection string, copy both the pooled "Transaction" string
   (port 6543, `?pgbouncer=true`) into `DATABASE_URL` and the direct
   "Session" string (port 5432) into `DIRECT_URL`. Run
   `npx prisma migrate deploy` against `DIRECT_URL` to create the schema.
2. Create a **Cloudinary** account and copy the Cloud Name/API Key/API
   Secret into your production env vars (see `.env.example` and the
   README's "Image & file uploads" section) — needed before any CMS image
   uploads will work on the live site.
3. Run the migration scripts in `/migration-scripts` to → Cloudinary → Postgres path.

## 3. Zero-downtime domain cutover

DNS changes are never truly instant (TTL + resolver caching), so the goal is
to make the _transition window_ harmless rather than try to make DNS itself
instant.

### Step 1 — Lower TTL in advance

At least 24–48 hours before cutover, log into the current DNS provider
(likely cPanel/WHM's DNS zone, or wherever the domain's nameservers point)
and lower the TTL on the `A`/`CNAME` records for `crdph.org` and `www` to
**300 seconds (5 min)**. This isn't optional — it's what makes the actual
switch fast later.

### Step 2 — Add the domain in Vercel

In the Vercel project → **Settings → Domains**, add:

- `crdph.org`
- `www.crdph.org` (redirect to apex, or vice versa — pick one canonical host)

Vercel will show you the exact records to create:

- Apex domain (`crdph.org`): an `A` record → `76.76.21.21` (Vercel's anycast
  IP — confirm the current value in your dashboard, it can change) **or**
  ideally switch to Vercel's nameservers if you want Vercel to manage DNS
  entirely.
- `www`: `CNAME` → `cname.vercel-dns.com`

### Step 3 — Cut over at low-traffic time

Pick a low-traffic window (check your analytics for your quietest hours). At
that point, update the DNS records at the registrar/DNS provider to point to
Vercel as shown above. Do **not** delete the old records at the cPanel host
yet — you're changing where the domain _points_, not deleting the old server.

### Step 4 — Watch propagation

- Use `dig crdph.org` / `dig www.crdph.org` or https://dnschecker.org to watch
  the new records propagate globally. With a 300s TTL this is typically
  resolved everywhere within 15–60 minutes.
- Vercel automatically issues a free SSL certificate (via Let's Encrypt) for
  the domain once it verifies DNS ownership — usually within minutes of the
  DNS record appearing. No manual certificate work needed.

## 4. SEO preservation: 301 redirects

Already implemented in `next.config.js` (`legacyRedirects`) — every legacy
`.php` URL 301-redirects to its new route. This is critical: Google treats a
301 as "this content moved, transfer the ranking signal," while a plain 404
loses it.

After cutover:

1. In **Google Search Console**, submit the new `sitemap.xml`
   (`https://crdph.org/sitemap.xml`, already generated by `src/app/sitemap.ts`).
2. Use Search Console's URL Inspection tool to request re-indexing of the
   homepage and a few key pages to accelerate re-crawl.
3. Monitor the **Coverage** and **Redirects** reports over the following
   weeks for any old URL patterns you missed (e.g. `blog-details.php?id=N`
   links from external sites — see `migration-scripts/03-generate-id-redirects.ts`
   for generating precise per-ID redirects once content has real slugs).
4. Do **not** remove the redirects after a "grace period" — keep them
   indefinitely. They cost nothing and old backlinks/bookmarks persist for
   years.

## 5. Environment variables to set in Vercel

Copy every key from `.env.example` into Vercel → Settings → Environment
Variables. Set **Production** values from your Supabase production project
and live Cloudinary/Stripe/PayPal credentials; set separate **Preview**/
**Development** values (a Supabase branch or second project, Cloudinary test
folder, Stripe/PayPal test keys) so preview deployments never touch
production data or take real payments. At minimum:

- `DATABASE_URL`, `DIRECT_URL` — from Supabase (see §2 above; these are
  _different_ connection strings from the same project, not the same value
  twice)
- `AUTH_SECRET`
- `NEXT_PUBLIC_SITE_URL`
- `RESEND_API_KEY`, `CONTACT_INBOX_EMAIL`
- `CLOUDINARY_CLOUD_NAME`, `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`,
  `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`
- `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_PAYPAL_CLIENT_ID` — start with test/sandbox
  keys, verify a full payment flow end-to-end, then switch to live keys
- `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` — only needed once, to run
  `npm run seed` against production the first time; rotate the password via
  the database immediately after first CMS login

Never commit real values to git — `.env` is already gitignored.

## 6. Post-launch operational notes

- **Backups**: managed Postgres providers (Supabase/Neon/RDS) handle
  automated backups — confirm the retention window matches your comfort
  level (7–30 days is typical on free/low tiers).
- **CMS access**: the built-in `/admin` CMS is protected by NextAuth
  credentials against the `AdminUser` table. Seed the first account via
  `npm run seed` (uses `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` from env) and
  change the password immediately after first login — there's no self-serve
  password change UI in this starter yet, so plan to add one or rotate via
  the database directly early on.
- **Monitoring**: enable Vercel's built-in Web Analytics (privacy-friendly,
  no cookie banner needed) and Speed Insights from the project dashboard.
